BotQL:Bot Query Language

BotQL é uma linguagem de regras simples, inspirada em SQL, para criar bots sem precisar de escrever código tradicional.

Todos os comandos são escritos em MAIÚSCULAS. Blocos com mais de uma ação usam chaves { }.

Vive no mesmo ficheiro .sql, com comandos reais de banco de dados — o bot age e persiste dados na mesma linguagem, sem sair do BotQL.

Estrutura Geral

IMPORT {ficheiro.sql}

CREATE BOT "NomeDoBot"
PLATFORM <PLATAFORMA>

CONNECT <SERVIÇO> <TIPO> "<credencial>"

CREATE TABLE <tabela> (<colunas>) [PREVENT DEFAULT] [DEFAULT MESSAGE ...]

ON <EVENTO> {
<AÇÃO>
<AÇÃO>
}

RUN BOT

CONTAINS: as três formas

Todas as formas de CONTAINS são case-insensitive ("OLA", "Ola" e "ola" batem todas com CONTAINS "ola") e podem ser combinadas com OR dentro do mesmo WHEN.

1. Palavra única (forma original)

WHEN CONTAINS "oi" OR CONTAINS "ola" {
REPLY "Ola! Como posso ajudar?"
}

Prático para 2-3 palavras. Para listas maiores, repetir OR CONTAINS fica longo e difícil de ler — usa-se uma das duas formas abaixo.

2. Lista inline

WHEN CONTAINS ("oi", "ola", "boa tarde", "boa noite", "bom dia") {
REPLY "Ola! Como posso ajudar?"
}

Basta uma das palavras da lista aparecer na mensagem para a condição ser verdadeira. Boa para listas de tamanho médio (5-20 palavras) que fazem sentido ficar visíveis dentro do próprio .sql.

3. Lista a partir de um ficheiro .txt

WHEN CONTAINS KEYWORDS(saudacoes.txt) {
REPLY "Ola! Como posso ajudar?"
}

Para listas grandes (100+ palavras) que poluiriam o .sql. O nome do ficheiro não leva aspas — é um nome de ficheiro, não uma string de busca.

O ficheiro é lido uma vez (e mantido em cache) na primeira mensagem que avalia essa condição, não a cada mensagem recebida.

Formato do .txt: uma palavra ou frase por linha, sem aspas, sem vírgulas, sem comentários, sem qualquer outra sintaxe misturada.

oi
ola
boa tarde
boa noite
bom dia

REPLY a partir de um ficheiro indexado

Além de REPLY "texto direto", o REPLY também lê uma entrada numerada de um ficheiro externo:

REPLY (respostas.txt, 1)

O ficheiro de entradas numeradas aceita duas formas, nunca misturadas dentro da mesma entrada — a forma escolhida para a entrada N é reconhecida automaticamente pelo que vem logo a seguir ao N-.

Forma 1 — uma linha só (N- valor)

1- Ola! Como posso ajudar?
2- Desculpe, nao percebi. Escreve "ajuda".

REPLY (respostas.txt, 1) procura a linha que começa por 1- e usa o texto a seguir ao traço, até ao fim da linha, como resposta.

Forma 2 — bloco entre chaves (N-{ ... })

Para respostas que precisam de mais de uma linha — texto com opções em lista, um bloco de HTML, um trecho de Markdown:

3-{
Qual serviço você quer?
- Suporte técnico
- Vendas
- Cancelar
}

Tudo entre a { que abre e a } que fecha pertence à entrada — incluindo quebras de linha. A leitura é rigorosa quanto ao aninhamento: se o conteúdo lá dentro também tiver chaves, essas contam para o aninhamento e não fecham a entrada antes da hora:

4-{
<div style="{color:red}">
<p>Formulário de contacto</p>
</div>
}

Uma { sem a } correspondente antes do fim do ficheiro é erro — nunca é ignorado silenciosamente.

Este é o mesmo formato de ficheiro usado por IMPORT {ficheiro.txt, N} e pelo ficheiro usado em WAITING(...).

IMPORT: as duas formas

1. Importar outro ficheiro .sql

IMPORT {respostas.sql}
IMPORT {sinais.sql}

CREATE BOT "MeuBot"
PLATFORM WHATSAPP

RUN BOT

Tal como o SOURCE do cliente MySQL ou o \i do psql, isto é o interpretador do BotQL que resolve: ao encontrar IMPORT {ficheiro.sql}, lê o ficheiro indicado e junta o conteúdo antes de processar o resto.

  • IMPORT é sempre resolvido antes de qualquer outro comando, independente de onde aparece no ficheiro.
  • Um ficheiro importado pode conter blocos ON prontos a usar.

2. Importar uma entrada de um ficheiro de valores

IMPORT {env.txt, 1}

Com um segundo argumento (o índice), o IMPORT não trata o ficheiro como código — lê só a entrada N (mesmo formato N-/N-{} do REPLY indexado).

Sem AS, o valor fica na variável genérica env. Com mais de um segredo, cada IMPORT deve ter o seu próprio alias:

IMPORT {env.txt, 1} AS K
IMPORT {env.txt, 2} AS TOKEN_WHATSAPP

Com AS, o valor fica acessível diretamente pelo nome do alias em qualquer expressão — sem AS, só é acessível como env.NOME_FICHEIRO.

CONNECT RESPONSE e Response(): ligar a uma IA

  • CONNECT RESPONSE <alias> — liga o bot a uma IA usando um valor já importado. Só estabelece a ligação, não dispara nada sozinho. O alias tem de corresponder a um IMPORT {..., N} AS <alias> já feito antes.
  • Response() — dispara o ciclo de vida: pega na mensagem atual do cliente, envia para a IA ligada, espera a resposta, e devolve esse texto onde for chamado.
IMPORT {env.txt, 1} AS K
CONNECT RESPONSE K              -- só liga, não faz nada sozinho

CREATE TABLE Context() PREVENT DEFAULT

ON MESSAGE {
INSERT INTO Context()

WHEN CONTAINS "preço" {
REPLY "Confira o nosso catálogo: link.com"
}

OTHERWISE {
REPLY Response()         -- aqui é que dispara: envia, espera, responde
}
}

RUN BOT

Padrão de uso mais comum: OTHERWISE { REPLY Response() } — quando nenhuma regra WHEN cobre a mensagem, a IA entra como fallback inteligente.

Com mais que uma IA ligada, cada uma com o seu alias:

IMPORT {env.txt, 1} AS A
IMPORT {env.txt, 2} AS B

CONNECT RESPONSE A
CONNECT RESPONSE B

Response() sozinho só faz sentido com uma IA ligada — com mais que uma é ambíguo (o bot recusa com erro listando os aliases). Com várias, Response(<alias>) diz qual usar:

ON MESSAGE {
WHEN CONTAINS "vendas" {
REPLY Response(A)
}

WHEN CONTAINS "suporte" {
REPLY Response(B)
}

OTHERWISE {
REPLY Response(A)
}
}

O alias passado a Response(...) tem de corresponder a um CONNECT RESPONSE <alias> já feito antes — senão é erro.

THINK: retrieval local sobre um ficheiro de conhecimento

Diferente de REPLY (ficheiro, N) e de Response(), THINK procura, dentro do próprio dispositivo, o conteúdo mais relevante para a mensagem recebida, num ficheiro de conhecimento em texto livre. Não usa IA, não sai para a rede, não precisa de CONNECT nenhum.

WHEN CONTAINS KEYWORDS(perguntas.txt)
THINK(conhecimento.txt) OR
REPLY (fallback.txt, 1)

Formato do ficheiro de conhecimento: blocos de texto livre, cada um separado por uma linha em branco:

Entregamos em toda Luanda, com prazo de 2 a 3 dias uteis apos confirmacao
do pagamento.

Aceitamos pagamento via transferencia bancaria, multicaixa express ou
dinheiro na entrega.

O horario de atendimento e de segunda a sexta, das 8h as 18h.

Comportamento

THINK(ficheiro.txt) sozinho já é a resposta quando encontra algo com confiança suficiente — não precisa de REPLY THINK(...) antes. Só o fallback (opcional, depois do OR) precisa da palavra REPLY de facto.

Quando mais de uma parte do ficheiro parece relevante, THINK tenta perceber o motivo antes de decidir:

  • Informação repetida. Se os candidatos dizem basicamente a mesma coisa, responde com um deles, sem repetir.
  • Informação complementar. Se cobrem casos diferentes do mesmo assunto, tenta juntar numa única resposta.
  • Pergunta pouco clara. Tenta entender de novo, focando no que é mais decisivo, antes de desistir.

Só depois de esgotar essas tentativas: se nada bater com confiança suficiente, corre o REPLY (...) a seguir ao OR. Sem fallback e sem confiança, THINK não responde nada.

WAITING: texto e animação enquanto algo demora

Por omissão, sem nada extra no .sql, mostra um texto genérico tipo "Pensando..." e um tempo mínimo de 3 segundos, mesmo que a busca seja mais rápida — sem esse mínimo, a mensagem apareceria e desapareceria rápido demais.

1. Acoplado a um THINK, logo a seguir a ele, antes do OR:

THINK(conhecimento.txt) WAITING(loading.txt, 2) OR
REPLY (fallback.txt, 1)

2. Sozinho, como ação independente — útil antes de qualquer outra coisa lenta sem aviso próprio, como Response():

WHEN CONTAINS "vendas" {
WAITING("Um momento...")
REPLY Response(A)
}

Nos dois casos: primeiro argumento (opcional) — texto direto entre aspas, ou nome de ficheiro .txt (sem aspas). Sem argumento, usa o texto padrão. Segundo argumento (opcional) — segundos mínimos de espera. Sem argumento, usa 3 segundos.

Um ficheiro de WAITING pode conter HTML/CSS (plataformas de texto simples como o WhatsApp ignoram a marcação e usam só o texto):

<div class="pensando">
<span>A verificar a melhor resposta...</span>
</div>

Como a relevância é calculada

  • Frequência ponderada — palavra rara pesa mais que uma comum; repetições contam cada vez menos.
  • Correspondência de frase — um trecho de 2+ palavras igual conta mais que palavras espalhadas.
  • Tolerância a erros de escrita — 1-2 letras trocadas ainda pode bater, com peso reduzido.
  • Variações de plural/sufixo — "produtos" e "produto" contam como a mesma palavra.

O THINK não entende sinónimos sem raiz/letras parecidas — "horas" e "horário" continuam palavras diferentes. Para esses casos, é possível ligar manualmente um termo a outro nas opções do interpretador.

O ficheiro de conhecimento é lido e processado uma vez (cache), não a cada mensagem.

SHOW CATALOG / SHOW CATEGORY: catálogo de produtos a partir de um ficheiro

Mostra os itens (ou as categorias) de um ficheiro de catálogo — útil para lojas, menus, listas de serviços. Duas formas:

1. SHOW CATEGORY(ficheiro.txt) — sozinho, sem estar preso a um CATALOG. Mostra só os nomes das categorias do ficheiro:

WHEN CONTAINS "categorias"{
SHOW CATEGORY(catalogo.txt)
}

2. SHOW CATALOG(ficheiro.txt) — mostra os itens (nome, preço, cor, imagem). Sem CATEGORY, mostra os itens de todas as categorias juntas; com CATEGORY("..."), só os dessa categoria:

WHEN CONTAINS "tudo"{
SHOW CATALOG(catalogo.txt)
}

WHEN CONTAINS "bebidas"{
SHOW CATALOG(catalogo.txt) CATEGORY("Bebidas")
}

Formato do ficheiro de catálogo: um bloco por categoria, cada ITEM com nome entre aspas e modificadores opcionais PRICE, COLOR e IMAGE:

Bebidas {
ITEM "Coca-Cola 350ml" PRICE "500 Kz"
ITEM "Sumo de manga" PRICE "450 Kz" COLOR "#F5A623"
}

Snacks {
ITEM "Batata frita" PRICE "700 Kz" COLOR "#F5D76E" IMAGE "batata.png"
}

Comportamento

Tal como o resto do BotQL, a resposta chega sempre em duas formas ao mesmo tempo, no mesmo evento — quem recebe é que escolhe qual usar:

  • Texto limpo, sem marcação nenhuma — usado por plataformas de texto simples (WhatsApp, terminal).
  • HTML autossuficiente, com o próprio <style> embutido — usado pelo preview do editor e pelo chat de um Servidor BotQL.

Os cards de item vêm marcados com data-botql-produto="Nome do item", e cada categoria (no SHOW CATEGORY) com data-botql-categoria="Nome". O bot nunca executa nada sozinho a partir de um clique — só recebe, depois, a mensagem de texto normal que o próprio cliente enviar (é o host — o chat.html ou o preview — que decide o que escrever no campo de mensagem quando alguém toca num card).

DEFAULT MESSAGE: saudação automática ao primeiro contacto

Sem integração de plataforma, o BotQL não tem como "falar primeiro" sozinho. DEFAULT MESSAGE resolve isto usando o próprio banco de dados do bot para detetar se é a primeira vez que um client aparece.

É um modificador do CREATE TABLE, ao lado de PREVENT DEFAULT:

CREATE TABLE Context() PREVENT DEFAULT
DEFAULT MESSAGE "Ola! Bem-vindo."

Funciona com tabela manual também, desde que tenha coluna para o remetente (client ou sender):

CREATE TABLE messages (
id INT PRIMARY KEY AUTO_INCREMENT,
sender TEXT,
content TEXT,
reply TEXT,
created_at DATETIME
) PREVENT DEFAULT
DEFAULT MESSAGE "Ola! Bem-vindo."

Também aceita ficheiro indexado:

DEFAULT MESSAGE (greets.txt, 1)

Comportamento

Antes de correr o resto do ON MESSAGE, verifica se já existe linha na tabela para o client da mensagem:

  • Se não existir — primeira mensagem. Responde com a DEFAULT MESSAGE e não corre o resto do bloco dessa vez.
  • Se já existir — o ON MESSAGE corre normalmente, sem repetir a saudação.

A convenção env.txt

Para chaves de API, tokens e outros dados sensíveis, a convenção é concentrar tudo num único ficheiro env.txt, com uma entrada numerada por serviço:

1- sk-abc123suachaveaqui
2- outrachavesecreta

Cada IMPORT {env.txt, N} lê uma linha específica. Isto mantém segredos fora do .sql principal e fora de qualquer ficheiro partilhado ou publicado.

Segurança: env.txt nunca vai para o repositório

Um projeto BotQL pode ser público no GitHub sem nunca expor chaves de API — desde que env.txt fique de fora do repositório.

O projeto deve ter um .gitignore na raiz com a linha:

env.txt

Cada pessoa que usa o projeto cria o próprio env.txt localmente — o ficheiro nunca é partilhado nem fica público.

Eventos disponíveis

  • ON START — corre uma vez, quando o bot liga.
  • ON MESSAGE — corre sempre que chega uma mensagem.
  • ON SIGNAL FROM "<origem>" — corre quando chega um sinal de um canal específico.

Variáveis implícitas

BotQL não usa notação de ponto (MESSAGE.TEXT não existe). Em vez disso:

VariávelDescrição
clientRemetente da mensagem recebida
messageTexto da mensagem recebida
lastMsgTexto da última resposta enviada pelo bot

Integração com Banco de Dados

1. Manual, com colunas explícitas:

CREATE TABLE messages (
id INT PRIMARY KEY AUTO_INCREMENT,
sender TEXT,
content TEXT,
reply TEXT,
created_at DATETIME
) PREVENT DEFAULT

2. Automática, via Context():

CREATE TABLE Context() PREVENT DEFAULT

O INSERT também é automático:

INSERT INTO Context()

Regra fixa de ordem — INSERT sempre primeiro, UPDATE sempre no fim

  1. INSERT logo no início, antes de qualquer WHEN.
  2. Os blocos WHEN/OTHERWISE decidem a resposta.
  3. UPDATE sempre no fim, com LAST_INSERT_ID().
ON MESSAGE {
-- 1. INSERT primeiro
INSERT INTO messages (sender, content, created_at)
VALUES (client, message, NOW())

-- 2. WHEN decide a resposta
WHEN CONTAINS "preço" {
REPLY "Confira o nosso catálogo: link.com"
}
OTHERWISE {
REPLY "Desculpe, não entendi."
}

-- 3. UPDATE por último
UPDATE messages
SET reply = lastMsg
WHERE id = LAST_INSERT_ID()
}

content TEXT,
reply TEXT,

) PREVENT DEFAULT

WHERE id = LAST_INSERT_ID()

CREATE BOT "LojaBot"
PLATFORM WHATSAPP

CREATE TABLE Context() PREVENT DEFAULT
DEFAULT MESSAGE "Ola! Bem-vindo. Pergunte-me sobre entregas, pagamento ou horario."

ON MESSAGE {
INSERT INTO Context()

WHEN CONTAINS ("oi", "ola") {
REPLY "Em que mais posso ajudar?"
}

OTHERWISE
THINK(conhecimento.txt) WAITING(loading.txt, 2) OR
REPLY (fallback.txt, 1)
}

RUN BOT

Neste exemplo, a DEFAULT MESSAGE só é enviada na primeira mensagem de cada client novo; a partir da segunda mensagem, o fluxo normal já corre sempre.

Regras de sintaxe

  1. Todo comando é escrito em MAIÚSCULAS.
  2. Texto literal vai sempre entre aspas " ".
  3. Blocos com mais de uma ação usam chaves { }, sempre a seguir a ON ou WHEN.
  4. Uma única ação não precisa de chaves.
  5. WHEN só pode ser usado dentro de um bloco ON MESSAGE { }.
  6. OTHERWISE é opcional, mas recomendado.
  7. Não existe notação de ponto — usa-se client, message, lastMsg.
  8. PREVENT DEFAULT no CREATE TABLE evita erro se a tabela já existir.
  9. Context() é o único nome de tabela reservado — schema automático, INSERT INTO Context() também automático.
  10. Ordem fixa quando há BD: INSERT no início → WHEN/OTHERWISE no meio → UPDATE no fim, com LAST_INSERT_ID().
  11. { } a seguir a IMPORT é referência a ficheiro, não bloco de ações.
  12. CONTAINS (...) aceita lista de strings entre parênteses.
  13. CONTAINS KEYWORDS(ficheiro.txt) — nome do ficheiro sem aspas, só palavras-chave uma por linha.
  14. REPLY (ficheiro.txt, N) — formas N- valor ou N-{ ... }, nunca misturadas; chave por fechar é erro.
  15. Segredos vivem em env.txt, nunca no repositório (.gitignore).
  16. IMPORT {..., N} AS <alias> dá nome ao valor; sem AS cai em env.NOME_FICHEIRO.
  17. CONNECT RESPONSE <alias> só liga; Response()/Response(<alias>) é que dispara.
  18. Nomes de ficheiro só reconhecem letras, números e underscore — hífen não funciona.
  19. THINK(ficheiro.txt) sozinho já é a resposta quando tem confiança suficiente.
  20. WAITING(...) acoplado a THINK ou sozinho; argumentos opcionais e independentes.
  21. DEFAULT MESSAGE vai sempre dentro do CREATE TABLE, ao lado de PREVENT DEFAULT.
  22. SHOW CATEGORY(ficheiro.txt) sozinho mostra só nomes; SHOW CATALOG(ficheiro.txt) mostra itens, com CATEGORY("...") opcional para filtrar uma só.

Filosofia

BotQL não é uma linguagem de programação — é uma linguagem de regras para criar bots, tal como uma consulta SQL descreve o que queres buscar numa base de dados. Não precisas de saber programar para escrever BotQL; precisas apenas de saber o que queres que o teu bot faça.

Onde o bot corre

O interpretador vive num sítio fixo (GitHub), e cada utilizador só precisa do seu próprio ficheiro .sql com as regras do bot.

O bot corre localmente, no computador ou servidor do próprio utilizador — não em servidores geridos por terceiros. Fica online enquanto esse processo estiver a correr; manter o bot sempre online (PM2, screen, servidor próprio) é responsabilidade de quem o cria.
